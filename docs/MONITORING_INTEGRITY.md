# Monitoring integrity and diagnostic export

Sign in as an administrator and select **Monitor service health**. The existing **See what needs attention** panel now validates the complete monitoring response, expires old component health while the page is open, clears the display during refresh and exports a bounded diagnostic JSON. Other roles cannot use the panel or its authenticated API. Credentials, research histories, models and all 64 workspaces are unchanged.

## Correctness changes

The previous renderer checked only part of the payload and relied on a later response to replace an old healthy display. The revised contract verifies the process identifier, expected metadata, three named boolean components, status counters, finite/nonnegative timings, bounded event arrays, timestamps and the relationship between component availability, snapshot persistence and a healthy/degraded claim. Contradictory, incomplete or unexpectedly extended metadata is withheld. This protects this display/export contract; it is not independent attestation of the server or a security audit.

Server component evidence is unknown at the 90-second boundary. Missing samples, empty probe configuration, backward/non-finite observation clocks and unestablished uptime no longer turn into a healthy or zero-age claim. Sample age is rounded conservatively, so a rounded 90-second observation is withheld. Actual database/model/provider probes remain the same; an artifact checksum or model listing does not demonstrate successful inference/generation, model quality or operational readiness.

Invalid elapsed measurements are counted separately and omitted from the latency window rather than clamped to zero. Status counts still include those responses. Up to 200 accepted timing samples determine p95; invalid sample count is cumulative since process restart. Non-HTTP status values become `other` and cannot fabricate HTTP 5xx events. Only genuine 500–599 status codes enter the bounded failure list. Older complete snapshots without the new invalid-timing field remain readable and display **Not reported by this snapshot**, rather than an inferred zero. No database migration is introduced.

At receipt, the browser compares the server's sample age with its timestamp against the browser clock. It uses the larger age and then advances that age using elapsed monotonic browser time. A timestamp more than five seconds ahead of receipt makes current health unknown; an old/replayed sample is not refreshed merely by its arrival. The display schedules expiry and recomputes it on visibility changes and export. It never promotes server-reported unknown health to healthy. Browser scheduling/suspension can delay painting; this is not an independent uptime observer or a guarantee while the browser/computer is stopped. Clock checks are conservative comparisons, not authenticated clock synchronization.

Refresh immediately removes the previous result and disables export until a complete response is validated. Failure leaves current health unknown. A new session/sign-out aborts requests and invalidates late responses, including an old failure arriving after a newer session has loaded valid data. The poll interval remains 30 seconds. Response counts, events and timings are explicitly received snapshots, not constantly updating totals. Component state can become unknown while those recorded aggregate observations remain available.

## Diagnostic scope and privacy

**Export diagnostic JSON** includes the effective local state/age, known aggregate snapshot fields, receipt time and elapsed time. An expired or clock-inconsistent observation exports as unknown with its component badges removed. Unknown/disabled but otherwise valid observations can be exported for diagnosis; malformed/unreachable responses cannot. Export records `production_ready: false` and `external_alert_delivery: false`. There is no endpoint to import the export or mutate monitoring state.

The monitor retains no request bodies, scenarios, questions, route/query strings, credentials, account/session identifiers, IP addresses or exception text. Its identifier is a randomly generated process instance ID. Application/access logs are separate and not qualified by that statement. Local snapshots/events/counters remain ordinary mutable process/file observations. They reset on restart and are not a durable protected audit, independent alert service, semantic AI metric, service objective or production qualification.

## Observed checks

`reports/Monitoring_Integrity.json` records **13 passing in-process authenticated HTTP checks** with disposable accounts/database, synthetic component probes/clock/write failure and a real missing-model research API response. They cover anonymous/viewer denial, healthy/degraded/recovered observations, exact expiry, backward clock, persistence failure/recovery, invalid timing counts, a genuine HTTP 503 signal, redaction and restart not reusing old health. No real provider was stopped and no primary account, database or model was changed. Passwords/tokens stay in memory and are absent from the public report. These injected failures do not measure real outage recovery, capacity or production uptime.

Seven additional Python tests cover empty probes, conservative boundaries, invalid/backward clocks and JSON safety, invalid timing/status handling, bounded windows/restart and the disposable HTTP exercise. Three additional Node tests cover complete contract/arithmetic rejection, expiry/clock behavior and privacy/scoped export; the earlier renderer test now rejects malformed transition timestamps. **Eleven isolated browser cases** cover desktop, exact 390px mobile, automatic expiry without a response, contradictory state rejection/recovery, refresh clearing/outage recovery, viewer access, late sign-out/session replacement, future/replayed timestamps and old timing metadata. They use recorded disposable-check snapshots with simulated transport/receipt times and an accelerated expiry boundary, not a real user session or provider outage. See `reports/Monitoring_Integrity_Browser.json`.

Reproduce the HTTP exercise using `python -m infra.monitoring_check --output .local/new-monitoring-check`. The output directory must be new. The full Windows suite has **366 tests: 279 Python and 87 Node**; Linux skips the Windows DPAPI provider case. Existing monitoring and release evidence remains historical rather than being rewritten as proof of this change.

The production gaps remain: independent uptime checks, owned external alerts/escalation, centralized protected telemetry, semantic/pipeline monitoring, service objectives and cloud/security/recovery acceptance. All 24 production requirements remain open.
