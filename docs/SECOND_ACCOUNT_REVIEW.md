# Optional second-account research review

Before submitting an investigation, an author can select **Share this report with local researcher/admin accounts while pending and require a different account to review it**. This is off by default. Other examples reset this sharing selection, and old requests omit the false default, preserving existing request/report identities and review behavior. No saved report is automatically enrolled or shared.

Selecting the option shares the full pending report, including its question, tool evidence and source extracts, with eligible local researcher/admin accounts. A different eligible account opens it through the **Second-account review inbox** and records either reviewed as research or needs changes. The author cannot record either decision, including when the author is an admin. Review acceptance still requires the existing canonical evidence, citation, scope and coverage checks and the exact report fingerprint.

This is separation of local accounts, not proof of different people, organizational authority or independent operational approval. Anyone controlling two eligible local accounts can satisfy the account distinction. Managed identity, MFA, externally governed reviewer assignment and protected auditing remain outstanding. A second eligible account is required to use the opted-in workflow; this implementation does not create any real user accounts or change passwords.

## Access and transaction boundary

The authenticated, read-only `GET /api/v1/research/agent-review-inbox` is available to researchers/admins and lists at most 20 most recently updated pending reports from other accounts. It includes only explicitly opted-in reports with a valid exact-content fingerprint. The response contains run ID, author, objective and update time; it does not list observations or review notes. `has_more` explicitly reports additional eligible rows beyond the limit. The new endpoint accepts no query parameters. It uses an existing read-only/query-only database, a 250ms busy timeout and a cooperative three-second query/processing budget. Integrity or storage failure clears the result rather than returning partial metadata.

Opening an ID uses the existing `/api/v1/research/agent-jobs/{run_id}` endpoint. Non-admin peers gain read access only while that report is opted in and awaiting review, with its exact report hash intact. Other private reports remain hidden. Existing author/admin inspection rights are retained. Derived `review_access` flags guide the UI; they are not authority supplied by the browser or part of the report fingerprint.

`POST /api/v1/research/agent-review` keeps authentication, Origin and CSRF controls. The write transaction checks stored ownership, the opted-in policy, exact report hash/state and mechanical evidence quality again. For second-account decisions it additionally rechecks that the reviewer account is active with a researcher/admin role; HTTP calls recheck the current session's expiry and revocation inside that same transaction. An old middleware role/session cannot override these checks. The decision stores the reviewer account ID and a second-account marker alongside the existing actor, note, time and report fingerprint. Local mutable records are not tamper-proof audit evidence.

Concurrent reviewers serialize: one decision wins and later attempts cannot append a second decision. Completed reports leave the inbox and stop being available to ordinary peer reads; author/admin inspection remains. Opening never grants cancellation or general access to another user's history/archive. Already displayed or exported copies cannot be recalled. Shared and archived openings retain a display-selection guard: a delayed response cannot replace a newer report selection or edited input. A missing inbox entry is not proof that a particular review was saved; after an uncertain response, verify the recorded decision with the author/admin. This policy does not cancel running work or expire pending reports automatically.
